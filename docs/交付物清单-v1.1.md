## 一、v0.2 范围与结论

v0.2 把 v0.1 的“内存可自测机制”推进到“可接库、可走 HTTP、可挂 Skill、可被测试守门”的工程基线：

1. 持久化仓储：`internal/store` 聚合接口 + 内存/PostgreSQL 双实现；`deploy/migrations/001_init.sql`（12 个 CREATE TABLE，含核心表与事件表）。
2. MCP Skill Runtime：`internal/skillruntime`，协议版本 `2026-07-28`（无状态 JSON-RPC），initialize/tools/list/tools/call，门控错误码 -32001/-32002/-32003，内置 3 个 Skill。
3. 七个服务 HTTP JSON API 化：`internal/api`，保留 `-selftest` 自测；`bootstrap` 支持内存（默认）/ PG（`PG_DSN`）切换。
4. 真实 Go 测试套件：10 个包、53 个顶层测试函数，**52 PASS / 1 SKIP（PG 集成用例在无 PG_DSN 时跳过）/ 0 FAIL**，`-race` 全绿。
5. 全量关卡：`make test` / `make gate` 串起 build + vet + `go test -race` + 7 服务自测；docker-compose 首次启动自动挂 migrations；README 补全 HTTP 端点清单。

## 二、本轮新发现并修复的真实缺陷（不只是加测试）

| # | 缺陷 | 现象 | 根因 | 修复 |
|---|---|---|---|---|
| B1 | 消息序号跨用户空洞 | `go test -race ./internal/msgseq` 报 `user 21 gap 80 -> 82`（非 DATA RACE，是序号空洞） | `shard` 只有单个 `seq` 计数器，被哈希到同一分片的多个用户共用，互相插队导致每用户序号不连续，违背“会话内序号连续无空洞”契约 | `shard.seq` 改为 `map[uint64]uint64`（每用户独立计数，仍由分片锁保护）；`Next/NextBatch/Stats` 同步改造 |
| B2 | 陌生人“发送即扣费”审批通过后不扣款 | HTTP 端到端 `TestStrangerIntentSendChargeApprove` 账本仍为 PENDING | decide handler 用 `payload["billingMode"].(float64)` 断言，内存存储下 payload 是 `int`（只有 PG JSONB/HTTP 往返才是 float64），断言失败静默跳过扣款 | 新增 `toInt(any)` 兼容 int/int64/float64 |

修复后全量 `go test -race ./...` 全绿。

## 六、与 v0.1 的兼容性

- 七个服务的 `-selftest` 全部保留且仍通过，核心机制行为无回归。
- 服务默认内存存储，行为与 v0.1 一致；PG 为 opt-in（`PG_DSN`），不改变默认离线体验。
- HTTP 为新增对外能力，不影响原有自测入口。
