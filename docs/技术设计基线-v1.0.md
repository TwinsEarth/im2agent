## 0. 文档定位与核心原则

本文档是产品的技术设计基线，回答"用什么框架、定什么协议、怎么分层、先做什么"。

**唯一核心原则：把"Agent 能做什么"与"系统允许它做什么"分成两个独立层。**
模型负责决策意图；Harness 与权限门控负责执行边界。凡涉及信任档位、付费扣费、硬件音频出端、对外承诺的操作，一律不依赖模型"自觉遵守"，而由代码层的状态机和门控强制执行。

**三条不可妥协的产品原则：**

1. **付费永远发生在 Agent 预审之后**，付费不是"买通路"，是"买已被 Agent 预审过的有效触点"。这是防止付费机制被包装成"绕过过滤漏洞"的底线。
2. **信任边界是代码层的 capability 门控**，不是提示词约束。每个子 Agent 的每次工具调用都经过 Trust Zone 检查。
3. **"不上传原始音频"必须可验证，而不是可声明**。端侧只做唤醒/意图粗分类/敏感前置过滤，原始音频不离开设备；需要上云的语音片段由用户显式触发，并产生可审计的传输事件。

## 1. 产品形态

### 1.1 Agent 体系：总 Agent → 子 Agent → Skill 三级结构

| 层级 | 产品命名 | 职责 | 用户可见性 |
|---|---|---|---|
| L0 | 总 Agent（管家/秘书/助理） | 任务路由、优先级仲裁、跨子 Agent 协调、最终呈报 | 始终可见，用户的第一界面 |
| L1 | 子 Agent（专家） | 单领域闭环：工作邮件、采购比价、物业报修、法律、日程预约、陌生人电话过滤、家政、维修、教育、亲子等 | 按需激活，用户可查看状态 |
| L2 | Skill/插件 | 原子能力：调用 API、执行脚本、查询数据库 | 不直接暴露，仅在审批链中展示调用记录 |

**"分类 & 专家 & 蒸馏自己"的工程化**：用户的每次审批/驳回/修改都是对 Agent 行为的反馈信号。编排层把反馈写入 Improvement Memory，根据驳回率自动收紧子 Agent 的自动决策阈值（例：采购子 Agent 连续三次比价被驳回 → 资金类操作自动执行额度下调一档，更多中间步骤转为人工审批）。这一闭环不需要修改基座模型权重，完全在编排层完成，是产品差异化的真正来源。

### 1.2 24 小时随身硬件

- **首发硬件：耳夹式耳机**（非眼镜）。佩戴门槛低、全天佩戴社会接受度高；"接电话/听留言/语音审批"是最高频 Agent 交互，耳机比眼镜自然。
- **第二形态：AI 眼镜**（面向第一视角拍摄、翻译、会议记录的进阶用户）。
- **远期形态：指环/夹子**（健康监测+触觉通知；环境音频采集）。供应链与交互范式不成熟，不做首发。
- **"24 小时在线"的工程定义**：不是单次充电续航 24 小时，而是"换电/充电盒覆盖全天 + 低功耗待机时 Agent 仍在线"。Agent 在线是云端/手机侧能力；硬件待机只维持 BLE 连接和语音唤醒，不持续上传音频。
- **硬件隐私为强制规格**：麦克风/摄像头启用指示灯、物理静音开关、最小必要采集、端侧优先处理（参照《AI 眼镜可信视界自律公约》）。隐私指示不是可选项。

### 1.3 陌生人付费消息：两档可组合计费

| 模式 | 计费触发 | 适用场景 | 风控要点 |
|---|---|---|---|
| 发送即扣费 | 点击"发送消息"即扣费（无论是否阅读） | 明确商业询盘、紧急事务 | 费率极低（象征性），用于过滤批量垃圾 |
| 看到且回复才扣费 | 消息先进入对方 Agent 筛选队列，本人点击"查看并回复"才扣费 | 高价值人脉、专家咨询、猎头 | 单日发送次数上限，防止付费方滥用 |

**关键机制**：付费之前，双方 Agent 团队必须先完成一轮"方案级讨论"——陌生人的 Agent 向目标用户的 Agent 提交结构化来意（谁、为什么联系、期望什么、紧急程度），目标 Agent 按用户预设规则（如"只接受工作相关询盘"）决定是否推送本人。只有被推送的消息进入付费环节。

### 1.4 熟人权限：五档信任矩阵

| 档位 | 典型关系 | Agent 可自主执行 | 需用户审批 | 禁止 |
|---|---|---|---|---|
| L0 本人 | 用户自己 | 全部 | — | — |
| L1 家庭 | 配偶、父母、子女 | 日程协调、家庭采购、物业事务 | 大额支出、对外承诺 | 查看工作子 Agent |
| L2 信任 | 密友、长期同事 | 预约日程、留言转达 | 涉及第三方信息查看 | 家庭事务 |
| L3 已知 | 普通熟人、校友 | 接收留言并摘要 | 所有对外回复 | 主动发起联系 |
| L4 陌生 | 无关系 | 仅接收结构化来意 | 付费后查看 | 任何自主执行 |

工程实现是代码层 Trust Zone Capability 检查（见 §3.3），不是提示词。

## 2. 总体架构

### 2.1 分层架构

```
┌─────────────────────────────────────────────────────────────────────┐
│ L1 接入层                                                           │
│   可穿戴(耳机/眼镜, BLE→手机) · 手机 Flutter · PC Flutter · 手表     │
├─────────────────────────────────────────────────────────────────────┤
│ L2 边缘/端侧层（手机 App 承担）                                      │
│   端侧ASR/意图粗分类 · 敏感前置过滤 · 离线审批缓存 · BLE 网关         │
├─────────────────────────────────────────────────────────────────────┤
│ L3 IM 通信层（公有云 PaaS，Phase 0-1）                               │
│   长连接 · 多端同步 · 离线推送 · 群组消息分发                        │
├─────────────────────────────────────────────────────────────────────┤
│ L4 Agent 编排层（自研，核心资产）                                    │
│   Agent Registry │ Skill Runtime │ 审批工作流引擎 │ 权限门控         │
│   记忆分层        │ 出口护栏      │ Agent协商通道(gRPC,独立于IM)     │
├─────────────────────────────────────────────────────────────────────┤
│ L5 模型层                                                            │
│   端侧小模型(唤醒/意图/过滤)  ←→  云端大模型(规划/协商/专业推理)     │
├─────────────────────────────────────────────────────────────────────┤
│ L6 数据层                                                            │
│   PostgreSQL(关系链/权限/账本) · 对象存储+OpenSearch(消息归档)        │
│   pgvector(Agent记忆向量) · 时序库(设备遥测) · 审计日志(不可变)       │
└─────────────────────────────────────────────────────────────────────┘
```

### 2.2 三条关键流量分离（本架构最核心的决策）

| 流量 | 通道 | 特征 | 说明 |
|---|---|---|---|
| 人类 IM 消息 | 公有云 IM PaaS 长连接 | 低频、需离线到达、需多端同步 | 文字/语音/图片/审批卡片/群组 |
| Agent 间协商 | 自研 gRPC 双向流 | 高频、结构化、有状态 | 来意筛选、日程协调、方案讨论；**不经过 IM PaaS** |
| 审批与审计事件 | 内部消息队列（Kafka） | 高吞吐、可追溯 | 每次工具调用/门控放行或拦截/扣费均写事件 |

理由：Agent 协商若走 IM 长连接，会污染推送计数、干扰未读体系、无法做细粒度权限审计；审计事件必须与业务消息分离，才能支撑可解释性与合规追溯。协商的最终产物（审批卡片、来意摘要）再注入 IM 会话呈现给人类。

### 2.3 通道一：人类 IM 通道选型

- **Phase 0—1：腾讯云 IM PaaS**（WebSocket 长连接、离线推送、多端同步、群组能力，SDK 覆盖 Android/iOS/Windows/Web/Flutter，支持私有化部署）。目的：上线时间从"月"压缩到"周"，工程资源集中在 Agent 编排层。
- **自研网关触发条件**：Agent 协商流量占比超过总消息量 30%，或 PaaS 推送延迟 P99 超过审批卡片可接受阈值（建议 2s）。自研参考实现：Go-Zero + WebSocket + gRPC（im-api 网关 / im-msggateway / msg.rpc→Kafka→im-msgtransfer 持久化 MongoDB / im-push）。
- **消息序号并发方案**：64 分片锁 + FNV 哈希（用户 ID 哈希到 64 个分片，分片独立加锁，锁竞争降低约 64 倍；单分片排队超阈值时动态拆片）；注册 Worker 与广播 Worker 分离，不争抢 goroutine 池；Kafka 按 msg-transfer / msg-push / msg-offline-push 三 topic 分流，消费端批量拉取 + 死信队列 + 指数退避。
- **边界**：IM PaaS 只负责"把消息送达设备"。登录鉴权、关系链、信任档位、付费消息状态机、Agent 协商路由、消息归档、全量审计全部自有。

### 2.4 通道二：Agent 协商通道

承载三类流量：陌生人来意协商、熟人事务协调（双方子 Agent 多轮方案交换）、跨组织委托（远期，A2A）。

内部协商协议参考 A2A 的 Task 状态机但使用**自定义 Protobuf schema + gRPC 双向流**（不走 A2A 完整规范——AgentCard 签名和发现机制是为互不信任的跨组织设计的，内部高频协商是纯开销）。状态机 8 态：`submitted → working → input-required / auth-required → completed / failed / canceled / rejected`。其中 `input-required` / `auth-required` 是"卡住但未失败"的中断态——分别对应"需要对方补充信息"和"需要用户审批下游动作"，**这正是人机混合审批的协议级落点**。

协商硬性约束：最大轮次（默认 5 轮）+ 总 token 预算，超限自动转 `input-required` 上抛用户；协商过程不产生用户可见通知，只在终止时生成一张审批卡片。

### 2.5 端侧—边缘—云端三级分流

| 位置 | 职责 | 明确不做什么 |
|---|---|---|
| 端侧（耳机/眼镜 SoC） | 唤醒词检测、VAD、敏感内容前置过滤、意图粗分类 | 不运行完整 Agent；不持续上传原始音频 |
| 手机 App（本地编排代理） | BLE 网关、网络请求转发、离线降级、审批缓存 | 不替代云端大脑 |
| 云端 | Agent 协商、多步规划、复杂子 Agent 委派、专业领域推理 | 不接收未显式触发的原始音频 |

端侧语音栈推荐：Sensory TrulyHandsFree/TrulyNatural 或 Ambiq soundKIT（KWS/VAD/说话人验证，兼容 TFLite Micro）；唤醒词模型用 CTC 端到端架构（穿戴设备实测约 93% 唤醒率、<100ms 启动）。候选硬件平台：恒玄/高通音频平台（感知节点定位）、Nordic nRF54L 系列（带 NPU 的超低功耗 SoC）。

## 3. 技术框架与选型

### 3.1 后端：Go-Zero 微服务（核心链路），Java 仅保留账本对账场景

- 服务间通信统一 gRPC + Protobuf；API 网关经 gRPC 网关转 REST；服务发现用 etcd。
- Go 在 WebSocket 长连接密集场景的内存占用远低于 Java，适合 IM 网关。
- Java 保留场景：支付账本与复杂对账逻辑（如团队 Java 生态更强），经 gRPC 与 Go 互通。IM 核心链路（网关/消息/Agent 编排）统一 Go。

### 3.2 客户端：Flutter 统一跨端（手机 + PC + 手表）

- 三端共享业务逻辑层；IM 类产品中 Flutter 已验证移动端/桌面端 UI 一致性。
- **手表端不做完整 IM**，只做三件事：审批卡片（是/否/稍后）、未读摘要、紧急联系人一键触发。手表是"决策端"而非"浏览端"。
- 硬件（耳机/眼镜）通过 BLE 与手机 App 通信，LE Audio 使用 LC3 编解码器；手机 App 承担 BLE 连接管理、网络请求与 Agent 编排负载。

### 3.3 Agent 编排层：参照 Harness² 八组件模型，自研编排内核

| 模块 | 职责 | 关键设计决策 |
|---|---|---|
| Agent Registry | 总/子 Agent 配置元数据 | 声明可用 Skill 白名单、记忆范围、信任档位权限上限、模型路由策略 |
| Skill Runtime | Skill 注册/发现/版本管理/沙箱执行 | 容器化沙箱 + 声明式权限清单（数据域/外部 API/是否涉资金） |
| 审批工作流引擎 | 生成审批单、驱动状态机、回写反馈 | 显式状态机，不依赖模型临场规划审批顺序 |
| 权限门控 | 每次工具调用的 Trust Zone 检查 | **代码层强制**，在 Skill Runtime 的 PreToolUse 钩子执行，模型无法绕过 |
| 记忆分层 | 工作/情景/语义记忆 | 子 Agent 记忆池隔离；总 Agent 只持有协调记忆，不读取子 Agent 原始记忆 |
| 出口护栏 | Agent 外发内容统一合规检查 | 所有 Agent 输出（含协商内容）必经检查，结果与 messageId 绑定写入审计 |

**蒸馏闭环**：审批反馈 → Improvement Memory → 自动调阈值 → 行为漂移监控（审批通过率/驳回率/用户修改率）。

### 3.4 数据层选型

| 数据域 | 选型 | 决策依据 |
|---|---|---|
| 关系链/信任档位/付费账本 | PostgreSQL | 强一致、ACID 事务、审计需求 |
| Agent 记忆向量 | pgvector（首发）→ Milvus（规模化后） | pgvector 数千万级向量内性能足够（P95≈25ms/600+RPS）；迁移判断：单用户向量 >50 万，或混合查询 P99 >200ms |
| 消息归档与全文检索 | 对象存储 + OpenSearch | 内容审核回溯、监管调取 |
| 协商状态与任务 | PostgreSQL + 内部消息队列 | 有状态长事务，需显式持久化 |
| 设备遥测 | 时序库（TimescaleDB/InfluxDB） | 仅设备状态和崩溃日志，不存原始音频 |
| 审计日志 | 不可变存储（对象存储 WORM / 专用审计库） | 扣费与 Agent 决策轨迹的追溯基础 |

## 4. 协议设计

### 4.1 协议全景

| 协议 | 作用域 | 传输绑定 | 使用阶段 |
|---|---|---|---|
| A2A v1.0 | 跨组织 Agent 协作 | JSON-RPC 2.0 / gRPC / HTTP+JSON | Phase 3 |
| MCP（2026-07-28 无状态核心） | Agent ↔ 工具/Skill | Streamable HTTP（无状态） | Phase 1 起 |
| 内部 Agent 协商协议（自定义 Protobuf） | 平台内总↔子 Agent、双方 Agent 协商 | gRPC 双向流 | Phase 0 起 |
| 审批工作流协议（自定义 Protobuf） | 编排层 ↔ 审批引擎 ↔ 客户端 | gRPC + 内部 MQ | Phase 0 起 |

### 4.2 A2A：只用于跨组织边界（Phase 3）

- A2A 是 Linux Foundation 托管的开放规范，v1.0.0（2026-03 发布），Python/Go/JS/Java/.NET 官方 SDK。核心设计原则："交换目标、不交换家底"——双方只交换能力声明（AgentCard）和任务结果。
- **Phase 0—2 内部不使用 A2A**；Phase 3 在边界网关实现 A2A Server/Client，对外 Agent 在内部转换为自定义协议。
- **必须自建验收层**：A2A 解决"怎么传"不解决"怎么信"。任务状态由执行方自报，签名名片只证明身份不证明履约质量。边界网关必须：该测的测、该留日志的留日志、该走人工审批的走审批，不能因协议返回 completed 就自动放行。
- **安全注意**：A2A v1.0.0 故意将授权排除在协议之外。Agent Card 必须由平台签名，发现请求必须经 Agent Registry 校验，不能直接信任外部 Agent Card（防 typosquatting / 注入篡改）。
- **授权自研（任务级授权令牌）**：每个 Agent 间 Task 携带由发起方用户签发的限定范围令牌（VC 风格），声明"允许就 X 事项、与 Y 身份范围、在 Z 时间窗口内协商，不得涉及资金/不得承诺时间"。接收方权限门控在执行工具调用前验证。

### 4.3 MCP：Skill 接入标准（无状态核心）

- MCP 2026-07-28 规范转向无状态核心：移除协议级初始化握手与 Mcp-Session-Id，每个请求自包含协议版本与能力，可路由到任意实例，适配 Serverless。
- 落地：每个子 Agent 作为 MCP Host，Skill 以无状态 MCP Server 形式注册并声明权限清单（readOnlyHint/destructiveHint）；授权对齐 OAuth 2.0 / OIDC。
- **Skill 沙箱**：每个 MCP Server 独立沙箱运行，权限门控代理（Permission Gate Proxy）拦截所有工具调用，检查三项：① 调用方 Agent 是否拥有该 Skill 声明权限；② 当前任务信任档位是否允许该操作；③ 是否在预算（金额/次数/时间）内。检查在代码层执行。
- 分层职责：MCP 负责"工具怎么被调用"，Harness 权限门控负责"这个调用是否被允许"，两者不在同一层，不能互相替代。

### 4.4 人类 IM 消息业务封装

```json
{
  "bizType": "APPROVAL_CARD | STRANGER_INTENT | AGENT_DIGEST | NORMAL_TEXT | ...",
  "bizId": "全局唯一业务ID",
  "payload": { },
  "traceId": "关联审计日志",
  "trustZone": "family | trusted | known | stranger",
  "agentContext": { "initiatorAgentId": "procurement-agent", "approvalState": "PENDING" }
}
```

**消息可靠性**：IM PaaS 承担传输层；业务层实现"至少一次投递 + 幂等去重"。每条业务消息携带单调递增 bizSeq（会话内保序），客户端维护 last_ack_seq，接收侧按 bizId 去重——确保付费扣费和审批状态的业务语义恰好执行一次。

## 5. SDK 设计

### 5.1 客户端 SDK：Flutter 统一 + 硬件 BLE 桥接

```
┌────────────────────────────────────────────┐
│ UI Layer（审批态 / 巡视态 / IM 会话）        │
├────────────────────────────────────────────┤
│ Business Controller Layer                  │
│   审批状态管理 · 信任档位展示 · 付费流程     │
├────────────────────────────────────────────┤
│ SDK Adapter Layer                          │
│   IM PaaS SDK 适配 · Agent 编排 API 客户端  │
│   BLE Manager（硬件桥接）                   │
├────────────────────────────────────────────┤
│ Local Persistence（Isar/sqflite，按 uid 分库）│
└────────────────────────────────────────────┘
```

硬件 BLE SDK：可穿戴设备不运行网络栈与 Agent 编排逻辑；硬件只负责语音采集/播放、唤醒词检测、端侧敏感过滤、审批指示（LED/触觉）。手机 App 作为 BLE 网关。

### 5.2 Agent 侧 SDK

- **Skill SDK**（面向内部/第三方开发者）：Python/TypeScript 绑定，封装 MCP Server 注册、权限声明、沙箱配置、测试桩。声明式清单：`skill_id/version`、`required_capabilities`、`financial_impact(none|read_only|spend_limit)`、`trust_zone_min`、`approval_policy(自动|需审批|需双重审批)`。
- **Harness SDK**（面向 Agent 开发者）：封装 Agent Loop、记忆读写、子 Agent 委派、出口护栏调用。**核心约束：Agent 代码不能直接调用外部 API 或数据库，所有外部操作必须经 Skill Runtime 的 MCP 通道**——确保权限门控与审计日志不被旁路。

## 6. 数据模型（核心表，PostgreSQL）

```sql
-- 信任档位
CREATE TABLE trust_levels (
  user_id BIGINT, target_id BIGINT,
  level SMALLINT CHECK (level IN (0,1,2,3,4)), -- 0本人 1家庭 2信任 3已知 4陌生
  granted_at TIMESTAMPTZ, expires_at TIMESTAMPTZ,
  PRIMARY KEY (user_id, target_id)
);

-- 付费消息账本（不可变，仅 INSERT）
CREATE TABLE paid_message_ledger (
  id BIGSERIAL PRIMARY KEY,
  message_id UUID NOT NULL,           -- 幂等唯一键
  sender_id BIGINT, receiver_id BIGINT,
  billing_mode SMALLINT,              -- 1发送即扣费 2回复才扣费
  amount_cents INT NOT NULL,
  status SMALLINT,                    -- PENDING / CHARGED / REFUNDED
  charged_at TIMESTAMPTZ, approval_card_id UUID,
  UNIQUE(message_id)
);

-- 审批单
CREATE TABLE approval_tickets (
  id UUID PRIMARY KEY,
  user_id BIGINT NOT NULL,
  source_agent_id VARCHAR(64),
  ticket_type VARCHAR(32),            -- NEGOTIATION / PAYMENT / SKILL_CALL / EXTERNAL_ACTION
  state VARCHAR(32) NOT NULL,
  payload JSONB NOT NULL,
  deadline TIMESTAMPTZ,
  created_at TIMESTAMPTZ DEFAULT now(),
  resolved_at TIMESTAMPTZ
);

-- Agent 能力声明（权限门控的数据来源）
CREATE TABLE agent_capabilities (
  agent_id VARCHAR(64) PRIMARY KEY,
  trust_level_min SMALLINT NOT NULL,
  allowed_skills TEXT[] NOT NULL,
  budget_cents_per_day INT,
  requires_approval_above_cents INT
);
```

**记忆存储隔离**：每个子 Agent 独立向量命名空间（pgvector agent_id 过滤列）；总 Agent 只持协调摘要；用户删除权按 agent_id + user_id 删除向量与原始消息，审计日志保留删除操作本身不保留内容。

## 7. 客户端与 UI 交互

### 7.1 核心交互范式："审批态"与"巡视态"

用户目标是"像大老板一样"，客户端设计重心不是聊天，而是**审批与巡视**：

- **审批态（默认态）**：进入 App 首先看到 Agent 团队呈报的待审批事项，按"紧急/重要"排序。审批卡片包含：哪个子 Agent 发起 → 做了什么/发现了什么 → 建议动作 → 涉及信任档位 → 一键通过/修改/驳回。**设计目标：30 秒内完成一次有效决策。**
- **巡视态**：各子 Agent 工作状态可视化（采购 Agent 正在比价三家、物业 Agent 已提交报修单、陌生人过滤 Agent 今日拦截 N 条放行 M 条）。可钻入任一子 Agent 查看完整执行轨迹（调用了什么 Skill、读写什么数据、产生什么中间结果）。
- **熟人 IM 会话**：保留传统聊天界面，增加"Agent 摘要"层（对方管家提议周四拜访，家庭 Agent 已确认时间，等待批准）。**人机混合的落点：Agent 承担协调/预约/确认的"行政层"，人只处理情感层和最终决策层。**

### 7.2 陌生人来意卡片

陌生人消息不进会话列表，先以"来意卡片"进入独立过滤器队列：对方 Agent 结构化来意、双方协商摘要、付费模式与金额。用户可选"忽略"（不扣费，对方收到礼貌拒绝）或"接受并查看"（触发扣费，展示原始消息）。**付费决策与注意力保护合并为一个动作。**

### 7.3 审批超时升级

审批单是长生命周期、可寻址实体：30 分钟未审批推送手表，2 小时未审批推送短信；支持幂等重试；状态持久化 PostgreSQL，不放在内存。

## 8. 运营、客服与运维

### 8.1 合规资质（上线前置条件）

| 资质 | 说明 |
|---|---|
| ICP 增值电信业务经营许可证（信息服务业务） | 注册资本 ≥100 万元 |
| 国内多方通信服务许可证 | 涉及多人实时语音/音视频通话；全网 ≥1000 万，地网 ≥100 万 |
| 通信安全三级等保认证 | 提前取得 |
| 实名认证 | 手机号/身份证真实身份认证 |
| 硬件专项合规 | 麦克风/摄像头启用指示灯、最小必要采集、生物特征数据本地优先（参照《AI 眼镜可信视界自律公约》） |

### 8.2 内容审核闭环

平台承担内容治理主体责任，不把审核完全外包给 IM PaaS 或模型厂商。"机审 → 人工复核 → 申诉 → 处罚"闭环：语音消息实时 AI 审核；Agent 生成的所有外发内容（含陌生人协商摘要）过审；付费消息扣费不能绕过审核。**统一出口护栏**：任何 Agent 向外发送的内容必经合规检查，结果与消息 ID 绑定写入审计日志。

### 8.3 Agent 行为审计与"可解释性"运营

用户必须能回答"我的 Agent 为什么替我说了这句话"。运维侧提供：Agent 决策轨迹回放（审批卡片背后的完整执行链：触发的 Skill、读取的记忆、调用的模型、耗时）；异常行为告警（频繁调用某 Skill、超预算、触碰信任边界 → 自动降级并通知）；"蒸馏"效果监控（各子 Agent 审批通过率/驳回率/用户修改率作为运营指标）。

### 8.4 客服分层

- **L1 机器人客服**：平台自有 Agent 覆盖硬件连接、计费争议、权限设置。
- **L2 人工客服**：付费消息退款争议、隐私投诉、账号封禁申诉。付费争议有明确 SLA（如 24h 首次响应），涉及真实资金。
- **L3 安全与合规响应**：审核申诉、执法调取、未成年人保护，7×24 值班。

### 8.5 硬件运维与售后

首发不做全自研硬件：基于成熟 SoC（恒玄/高通）+ ODM 合作，精力放在 Agent 软件与 IM 平台。耳机作为"耗材型入口"（定价千元内，软件订阅+付费消息抽成构成长期收入）；建立换修周转池（电池衰减、丢单耳高频场景，区域仓预置替换件，"先换后修"）。

## 9. 开发计划

### 9.1 阶段总览

| 阶段 | 周期 | 核心交付 | 技术里程碑 |
|---|---|---|---|
| Phase 0 | 0—4 月 | 合规资质 + 最小 Agent 闭环（手机/PC） | Agent 编排层 v0.1；审批工作流引擎；Go-Zero 骨架；腾讯云 IM 接入 |
| Phase 1 | 4—9 月 | 付费消息 + 熟人权限 + 耳夹式硬件首发 | MCP Skill Runtime；negotiation-svc；payment-svc；TFLite Micro 端侧唤醒；Flutter 手表审批端 |
| Phase 2 | 9—18 月 | 子 Agent 扩展 + 眼镜形态 + 蒸馏体系 | 权限门控全链路；出口护栏；Agent 行为监控；自研 IM 网关迁移评估 |
| Phase 3 | 18 月+ | A2A 边界网关 + Skill 开发者生态 | A2A Server/Client；外部 Agent 接入验收层；开放平台 |

### 9.2 Phase 0（0—4 月）：打地基

| 里程碑 | 交付物 | 技术要点 |
|---|---|---|
| Week 1—4 | 合规申报 + Go-Zero 骨架 + 腾讯云 IM 接入 | ICP/多方通信/等保并行申报；auth/user/relation/msg 服务；Flutter 手机+PC 基础 IM |
| Week 5—10 | Agent 编排层 v0.1 | 总 Agent + 3 子 Agent（日程/陌生人过滤/家庭事务）；审批状态机跑通最短闭环；权限门控以代码常量实现 |
| Week 11—16 | 端到端验证 | 手机麦克风替代硬件输入，验证"语音触发 Agent → 审批卡片 → 审批 → 执行"链路 |

**Go/No-Go（Phase 0）**：审批态周活跃使用率 ≥ 40%，单次审批决策中位时间 ≤ 30 秒。

### 9.3 Phase 1（4—9 月）：付费消息与硬件

- MCP Skill Runtime + negotiation-svc（gRPC 双向流 + 8 态 Task 状态机）+ payment-svc（幂等账本）。
- 耳夹式硬件 v1：恒玄/高通 SoC ODM，Sensory/Ambiq 端侧唤醒，BLE Audio LC3，手机 App 网络代理；定价千元内绑定 6 个月 Agent 订阅。
- 灰度：内部 1% → 核心 5% → 10% → 30%，每轮观察 24—48h，崩溃率 <0.1%；付费消息独立风控开关可远程关闭。

**Go/No-Go（Phase 1）**：付费消息 Agent 预审拦截率 ≥ 95%；硬件退货率 < 8%。

### 9.4 Phase 2（9—18 月）：规模化与蒸馏

- 权限门控从代码常量升级为动态策略引擎；出口护栏覆盖全部外发内容；Agent 行为监控仪表盘（蒸馏健康度指标）。
- 自研 IM 网关迁移评估（触发条件见 §2.3），分两步：先替换持久化与推送链路，再替换 WebSocket 网关；关系链与信任数据始终在自有 PostgreSQL。
- AI 眼镜 SKU：启用指示灯与物理静音开关为强制硬件规格。

**Go/No-Go（Phase 2）**：第三方 Skill 权限违规拦截率 100%；Agent 协商 Task 完成率 ≥ 90%。

### 9.5 Phase 3（18 月+）：Agent 协作网络

A2A 协商通道对外部 Agent 开放，但 Agent Registry 签名校验、信任档位映射、付费消息 Agent 预审前置原则不变。平台角色从"IM 产品"转向"个人 Agent 协作网络基础设施"，核心资产是关系链、信任治理与付费账本。

## 10. 关键风险与工程约束

| # | 风险 | 应对 |
|---|---|---|
| 1 | A2A 授权真空（上下文投毒、Agent Card 伪造、typosquatting） | Agent Card 平台签名 + Registry 校验 + 任务级授权令牌，Phase 1 必须上线，不等 Phase 2 |
| 2 | 付费扣费重复/丢失 | 扣费账本以 bizId/messageId 为唯一键，支付回调、消息投递、审批状态变更经同一业务事务 ID 关联，任一侧重试不产生二次扣费 |
| 3 | 腾讯云 IM 私有化与公有云功能差异 | Phase 0 向腾讯云申请私有化功能清单，逐项差距分析；关键功能缺失则自研网关迁移提前到 Phase 1 末 |
| 4 | pgvector 混合查询优化器次优执行计划 | 查询计划监控；召回率下降强制 EXACT 扫描或迁移 Milvus；Phase 0 建立性能 baseline |
| 5 | 端侧唤醒误触发/漏触发（嘈杂环境） | VAD 前置门控 + CTC 端到端唤醒；手机保留"手动触发 Agent"降级入口；验收同时考核误触发率（每小时 ≤1 次） |
| 6 | Agent 协商无限循环消耗推理资源 | 硬性最大轮次（默认 5）+ token 预算；超限转 input-required 上抛用户；negotiation-svc 实时计量，异常会话熔断 |
| 7 | 端侧"不上传原始音频"承诺失真 | 端侧只做唤醒/意图粗分类/敏感过滤；上云片段用户显式触发；设备侧产生可审计传输事件记录 |
| 8 | 大厂免费产品挤压 | 差异化不在"更聪明的 Agent"，在人机混合 IM 的社交网络效应 + 付费消息经济设计（熟人关系链是大厂不敢轻动的部分） |
| 9 | 付费消息催生新型滥用（杀猪盘等） | 付费永远发生在 Agent 预审之后；单日发送次数上限；协商内容抽检 |
